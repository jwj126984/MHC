# 优化报文处理逻辑 - 产品需求文档

## Overview
- **Summary**: 优化 CAN 通信模块的报文处理逻辑，以应对 5ms 周期的高流量报文，确保界面不会因为报文流量过大而卡死。
- **Purpose**: 提高系统在高流量报文场景下的性能和稳定性，确保界面流畅响应，同时保持报文处理的实时性。
- **Target Users**: 开发人员和最终用户，特别是需要处理高频 CAN 设备报文的场景。

## Goals
- 优化报文接收和处理逻辑，提高系统在高流量场景下的性能
- 确保界面在 5ms 周期报文流量下保持流畅响应
- 减少系统资源占用，特别是 CPU 和内存使用
- 保持报文处理的实时性和准确性
- 提高系统的稳定性和可靠性

## Non-Goals (Out of Scope)
- 不改变 CAN 设备的通信协议和数据格式
- 不修改 UI 界面的显示逻辑和布局
- 不影响现有的信号解析和故障检测功能
- 不改变现有的事件通知机制

## Background & Context
- 当前实现已经移除了消息队列，直接在接收回调中处理报文
- 报文周期为 5ms，意味着每秒可能接收 200 条报文
- 高流量场景下，界面可能会因为频繁更新而卡死
- 需要进一步优化报文处理和 UI 更新逻辑，以提高系统性能

## Functional Requirements
- **FR-1**: 优化接收回调逻辑，提高报文处理效率
- **FR-2**: 优化批量处理机制，减少 UI 更新频率
- **FR-3**: 优化主界面的消息处理逻辑，提高 UI 更新性能
- **FR-4**: 实现流量控制机制，避免系统过载
- **FR-5**: 保持报文处理的实时性和准确性

## Non-Functional Requirements
- **NFR-1**: 界面响应时间不超过 100ms
- **NFR-2**: CPU 占用不超过 50%
- **NFR-3**: 内存使用不超过 200MB
- **NFR-4**: 系统能够稳定处理 5ms 周期的报文流量
- **NFR-5**: 报文处理延迟不超过 50ms

## Constraints
- **Technical**: 必须保持与现有代码的兼容性，不破坏现有的事件通知机制
- **Business**: 实现时间不超过 1 个工作日
- **Dependencies**: 依赖 ZLG CAN 设备驱动库

## Assumptions
- CAN 设备的报文周期稳定在 5ms
- 系统硬件能够支持处理高频报文
- 优化后的代码不会影响系统的稳定性

## Acceptance Criteria

### AC-1: 高流量处理
- **Given**: CAN 设备以 5ms 周期发送报文
- **When**: 系统运行并接收报文
- **Then**: 界面保持流畅响应，不出现卡死现象
- **Verification**: `human-judgment`
- **Notes**: 验证界面在高流量场景下的响应速度

### AC-2: 性能优化
- **Given**: 系统运行中
- **When**: 监测系统资源使用情况
- **Then**: CPU 占用不超过 50%，内存使用不超过 200MB
- **Verification**: `programmatic`
- **Notes**: 对比优化前后的资源使用情况

### AC-3: 实时性
- **Given**: CAN 设备发送报文
- **When**: 系统接收到报文
- **Then**: 报文处理延迟不超过 50ms，界面更新及时
- **Verification**: `programmatic`
- **Notes**: 测量报文处理的延迟时间

### AC-4: 稳定性
- **Given**: 系统长时间运行在高流量场景下
- **When**: 连续运行 24 小时
- **Then**: 系统保持稳定，不出现崩溃或异常
- **Verification**: `programmatic`
- **Notes**: 长时间运行测试

### AC-5: 功能完整性
- **Given**: 系统运行中
- **When**: 检查所有现有功能
- **Then**: 所有现有功能保持不变，包括报文解析、信号值更新、故障检测等
- **Verification**: `human-judgment`
- **Notes**: 验证所有现有功能的正确性
